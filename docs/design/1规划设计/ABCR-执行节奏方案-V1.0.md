## 1. 每日 4 小时窗的结构

```
0:00–0:10  窗口自身：读昨日 PROGRESS.md 与 fable 留言（若有契约修订/裁决），确认当日任务卡
0:10–3:40  连续编码（工程包任务卡顺序执行；阻塞 >30 min → 记 BLOCKER 换下一张卡）
3:40–4:00  收工三件套：跑本日验收命令并把结果贴进 PROGRESS.md；git commit（[pkgX] 前缀）；更新任务卡状态
```

fable 的日常参与**仅限**：每日异步读三份 PROGRESS（≤20 min）、裁决 BLOCKER 与契约疑议、阶段门主持。fable 不写业务代码（阶段0 交付物除外）——这是楠指示的 token 经济结构：Opus 在冻结上下文内连续编码，fable 只花在裁决与验收上。

## 4. 工时与预算账

**工时**（4h/天 × 3 窗 × 6.5 天 ≈ 78 窗时 + fable ≈ 8h）：A ≈ 24h、B ≈ 30h、C ≈ 24h。三包自估的阶段1 全量工时（各 ≈16–22h）**大于**两个 4h 窗——这正是 R1 拆 core/full 的原因（AMENDMENT-30）：R1-core 只含闭环六步最小件（各包 ≈6–8h，两窗可完成），其余卡在阶段2 期间补齐、R2 前收口。B 最重——若 B 拖期，优先砍 parity 烟检与 3B 开发路径（W1 既定止损），主链（官方复现+闭环闭合）不砍。

**云预算**：W1 上限 ¥150（d4）；预估两云日合计 ¥40–100（24GB 卡 ¥2–3/h × 每日 6–10h）；85% 熔断线触发即冻结新任务等楠裁决。judge API（DeepSeek）：W1 量级数千次打分，预计 ≤¥30。

**token 经济**：三 Opus 窗各自一次性读入工程包（冻结上下文），阶段内不换文档、不读盘外资料；fable 消费集中在 R0 交付与两个阶段门。
