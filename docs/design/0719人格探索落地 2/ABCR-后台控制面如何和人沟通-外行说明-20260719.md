# 后台控制面如何和人沟通、确保人能看懂

可以把 ABCR 后台想成一间实验室的“总控室”。人不用认识程序、文件夹或命令，日常只面对飞书里的一个“研究驾驶舱”。把自己和 Claude 已经讨论好的实验目标书交给它，就能问进度、批准花钱、暂停实验、查看结果，或者追问“为什么停了”。后台虽由许多程序共同工作，对人始终只有这一个前门。

驾驶舱不会把技术日志直接扔给人。每件事都翻译成六句话：现在是什么状态；最后确认是什么时候；系统已经做了什么；下一步做什么；大约还要多久；是否真的需要人。不需要人时，它明确写“系统正在自动处理”；需要人时，只给一个可直接复制的动作，例如“批准 APR-17 a1b2c3 v3”，而不是让人研究报错。

状态词必须诚实。“已收到”只是进了收件箱；“已接手”表示有执行者领取；“运行中”必须有近期进度；“验证中”表示结果尚未独立检查；验证通过后才叫“完成”。因此，排队不会被说成正在做，进程还活着也不等于一切正常。数据过旧、来源损坏或无法确认时，界面直接写“状态未知”，绝不猜成成功。

颜色只表示行动紧迫度，不表示研究结论好坏。蓝色是正常进行，绿色是完成并通过检查，黄色是值得注意，红色是停止或证据可能无效，灰色是等待或未知。人格得分没有提高不是工程故障；漏数据、越界、复算不一致才会报警。

快道和证据道始终分开。快道用中性标签永久写“学习数据·不可引用”，并显示题数、seed、题目重叠和模型版本。值得认真验证时，人只需说“毕业这一针”，系统便用未见题生成正式目标书草稿。正式结果则显示审批、审计、独立复算和证据来源，避免把一次有趣的小试误当成可靠发现。

审批卡只回答人真正关心的事：这轮验证什么，测哪些人格，与父本差在哪里，用多少题和 seed，预计多少钱、多久，有没有异常，批准何时过期。人点或打字“批准”后，后台重新核对身份、批次和内容指纹。同一按钮按十次也只生效一次；实验内容若改变，旧批准自动失效。

发生故障时，总控室先自己处理。例如卡片可能写：“模型进程意外退出；已完成 12/20 题，现有结果安全；系统正从第 13 题恢复，预计 8–15 分钟。”这里的数字只是当次实测，不是固定保证。网络瞬断、进程崩溃等已知问题会有限续跑；题集越界、证据损坏或配置漂移则立即隔离，绝不偷偷修数据。未知代码问题会形成工程任务；只有真 Codex 隔离修复、独立验证和发布链都资格化后才自动执行，否则清楚显示“任务已排队·自动维修未资格化（BLOCKED）”，绝不假装正在修复。

驾驶舱采用“先结论、后证据”。首页只放待确认目标、快道学习、正式实验、轮报告、异常恢复、预算校准六块。想多看时，可从一轮逐层点到批次、运行、某一道题，最后看到真正送给模型的完整提示、输出、判分和原始裁判记录。系统还可把同一份只读快照同步到飞书文档供连续阅读；文档不能下命令，也不是第二套状态。每个数字都有出处，所以简单页面不牺牲可核查性。

一轮结束后，报告把“观察到什么”和“为什么可能如此”分开。机器可以指出数据质量、方差、混淆和下一实验建议，但每条建议都要附证据、竞争解释、区分实验，以及“结果相反时怎样更新判断”。它只能建议，不能改写人的目标，更不能自行开始下一轮。人继续和 Claude 思考，再把新目标书交回驾驶舱。

确保人能看懂，靠四条纪律：默认只说人要做的决定；同一状态永远用同一词；任何结论都能逐层下钻；系统不知道时就明确说不知道。人把精力放在人格理论、实验目标和反思上，后台负责执行、盯场、修复和整理证据，但永远不冒充人的科学判断。
