# 复盘:七轮对抗审查为什么每轮都新增 P0/P1(2026-07-25)

> 撰写:Fable5。性质:**纯回溯根因彻查,不是第八轮审查**(楠明令不做第八轮)。
> 方法:11-agent 工作流——4 段 session 考古(`871e3ba5` 全程 2204 行)+ git 修复链量化
> + 方案/runbook 验证哲学考证 + 测试盲区逐 P0 考证 → 根因综合 → **三视角对抗核验**
> (事实锚定/替代解释/完备性)。核验器抓出综合初稿的 7 处事实错误与 8 处遗漏,
> 本文均已修正吸收;凡数字皆经 git/一手文档复测。

## 0. 一句话结论

**七轮不是"修不好"的循环,而是对一份 2.59 万行、部署路径零执行记录的单提交交付,
做的七次分片首审**——库存缺陷逐面显影,每次显影都被 fail-closed×冻结树×一次性
genesis 的架构放大成"一整轮全链重走"。在固定受审面上,复审其实 ≤2 轮就干净;
"每轮都有新发现"是首审逐面推进的期望输出,不是发散。

## 2. 根因(经对抗核验修正后)

### 2.1 上游单根:codex 的交付形态 + 交付即失联

- 936fdd7 是**单提交 156 文件 +25910/−808**,commit message 一行标题;其部署关键
  路径(root ceremony、激活链、真实体量 manifest、账户供给)交付时**零执行记录**。
- 全部阻断级 P0(约 10 个:轮1×2、轮2 幻影、轮3 死锁、实机B gid、轮6 策略矛盾、
  轮7×4)**没有一个是修复引入的**——修复自引入流严格停在 P1 层。
- codex 失联的连锁代价:幻影工具无法问询只能整轮 panel 考古;楠拍板由 Fable5
  连夜代写 1333 行(dbcd965 一个提交的新增面 = 其余九个修复提交之和的 73%),
  这 1333 行正是轮3–5 自引入 P1 流的主要孵化器;作者=审查者=签名者,独立性
  只能靠 panel 租借。**按"轮"计,codex 缺席的解释力与基线库存同量级。**

### 2.2 仪器侧:1500 绿灯的世界与真实世界交集为空

量化(夹具=全套件最富的 Rig,真实=production-b65fdc2 实测):

| 维度 | 夹具世界 | 真实世界 | 差距 |
|---|---|---|---|
| 树文件数 | 39 | 20,417 | 523× |
| manifest | 6,965 B(launcher 夹具 1,560 B) | 23,926,062 B | 3,435×(距最小 4 MiB 上限尚差三个数量级) |
| 可执行条目 | 1 个(`#!/bin/sh exit 99` 壳桩) | 250 个(含会写 pyc 的真 CPython) | — |
| 身份 | uid 501,gid 一律 monkeypatch | root + 11 个专用服务账户/gid | root 语义**结构性不可测** |
| 启动路径 | 注入假 execve,预写 active.json | launchd → selector → launch,首次无 active.json | 死锁语义被夹具钉成同向绿灯 |

最讽刺的实证:`test_stable_launcher.py:146` 把**无 -B 的缺陷 argv 逐字断言为期望值**
——绿灯即缺陷本身。`verify_release_read_policy`(轮6 P0 所在)在 947a895 上
**零执行覆盖**。四处 manifest 上限从未进入任何夹具可触达范围。
单测验证"每个组件自己怎么想",从不验证"多个组件想的是不是同一件事"
(轮3 死锁、轮6 模式矛盾、轮7 尺寸矛盾全是组合性质缺陷)。

### 2.3 显影节奏是审查配给的人工产物,不全是"能力自然升级"

核验器的关键修正:轮6 P0(四组件对封印模式三同一反)是**纯静态矛盾**,自基线起
对任何通读者可见;轮7 的 manifest 体量自轮1 起就是已知产物属性(票据一直跟踪
file_count)。它们不需要 root、真机或新能力——需要的是**第六轮才第一次配齐的
5 视角打满 panel**(此前 3-agent、两度撞用量上限清零、中段审查刻意以"本批修复
diff"为边界、全文穷举第 5'' 轮才启用)。**若轮1 就有第六轮的配置,多数发现可
提前数轮。**"逐轮才捞出"相当程度上是审查预算逐轮追加的镜像。

### 2.4 修复自引入流:真实、可切断、但被节奏喂大

- 实证链:dbcd965 新文件 → 下轮 P1 就在该文件;2c8899f 的 deferred-ack 重写 →
  下轮 fence P1;d79298a 的 home 物化 → 下轮 symlink P1;947a895 加固 → 轮6 P1×3。
  最长自噬线:enqueue_conflict 语义**连写错四版横跨四轮**。
- 节奏证据(git 时间戳):dbcd965 02:06 → panel 抓 P0 02:20 → 2c8899f 02:35
  (**15 分钟完成一次并发语义重写**)→ panel 抓其新 P1 02:53 → d79298a 03:23。
  极限节奏从轮2 修复起就存在,早于楠 08:22 的"我要快"6 小时;ack 反转/fence
  分歧这类崩溃窗口缺陷正是该节奏的典型产物。
- 可切断的证据要如实打折:轮6 摘出后轮7 确无自引入 P0/P1(弱版本成立;轮7 有
  一条 P2 落在代写的 qualify 脚本,"100% 回到基线"不成立)。且轮7 唯一复审的
  11b4cc2 是净删除批,而最后一个加法批 b65fdc2(+102)**从未被审过**——
  "断流"是未观测,不是已证明。

### 2.5 放大器:fail-closed × 冻结树身份 × 一次性 genesis

任一字节不符=全链 BLOCKED,无降级通过;一字节修复=新 release 身份=重建+重验+
重签+人工重比对+新票据;genesis 不可排练、不可重试。**每个缺陷(无论大小)的
最小响应单位被架构定为"一整轮"**——这不制造缺陷,但决定了"有发现→又一轮"的
动力学,也是"永远修不完"观感的直接来源。受审面=封印全树 2 万文件,而非变更面:
与科学语义无关的外围脚本缺陷同样作废整个 release。

### 2.6 文档双权威与两轴漂移

部署权威是 1014 行 prose 扩展 runbook(419 行人工命令、150 行 sudo、**0 个测试**),
且**位于 git 仓与封印树之外**——整套 hash/fail-closed 完整性机器对部署权威本身
结构性失明。两轴漂移全程发生:①runbook vs 代码(幻影工具、"可重试"谎言、
enqueue_conflict 四版错);②仓外副本 vs 仓内副本(仓内 runbook 五轮修订,共享
副本冻在 07-23 08:42,"收编进仓"未决项从未闭合)。全 tests/ 对 runbook 零 grep
命中——没有任何自动断言"runbook 引用的文件存在于封印树"。本复盘当天还抓到同
族新实例:阶段1 最终版指引步骤 6 预期值残留上一版 `REL-40a2f210…`(已更正)。

### 2.7 独立性坍塌与补偿模型衰减

作者=签名者的四条补偿(票据 3e8c1d1a §0)是为 **+21/−13** 的最小 delta 设计的;
后续 delta 达 +1333/+425/+303/+339 时四条腿只剩 panel 一条在走,而 panel 两度
撞限清零、末批耗尽额度。近失(near-miss)要点名:panel 清零 #1 后以作者自查
放行了阶段1(先于该 delta 任何独立复核约 36 小时);轮2 P0 是在阶段1 判 PASS、
阶段2 指引已成稿之后才到——一次性 genesis 名额靠"空结果不算放行"+指引 HOLD
的纪律才没有永久烧在一个无法激活的 release 上。另:**人(楠)实机操作是除 panel
外唯一反复起效的外部视角**(哨兵 gid 之外,home 根因由楠自诊、git 假阴性首诊被
楠实测证伪),这层补偿此前未被计入。

## 3. 直接回答"为什么永远修不完修不好"

1. **"修不好"不成立**:固定受审面上复审 ≤2 轮即干净(-B 修复轮2 被判完备;
   轮6 P0 修复被轮7 独立裁定正确;激活链两轮后无新发现;runtime tree 四版未变
   ——真正跑进服务进程的代码从第二轮起零缺陷零改动)。
2. **"修不完"是三件事的叠加观感**:
   (a) 库存侧——零执行记录的 2.59 万行交付,阻断级库存深到第七轮仍在出货;
   (b) 仪器侧——库存只能靠人工审查+真机逐面显影,而审查配置逐轮才加满,
   于是库存分七次而非一次显影;
   (c) 架构侧——每次显影都触发全链重走,把"发现一个缺陷"放大成"又一整轮"。
3. **中段确有一段真实的自我追赶**(每轮 2–3 个自引入 P1,15 分钟级修复节奏是
   主要供给),它被摘出决定切断——但其权重按轮计约三成,不是主循环。
4. **无法宣布库存已空**:b65fdc2(4 个 P0 的修复)至今无任何非作者视角看过;
   部署管线仍无系统化验证机制。票据残余风险 §5 说得对——"是否继续是权衡问题
   而非技术问题"。

## 4. 现有决定化解了什么、还悬着什么

**已化解**:①摘出账户加固同时切断自引入流与受审面扩张(轮7 无自引入 P0/P1 为证);
②manifest 体量(>8 MiB 夹具)与封印模式(双向回归)两个缺陷族从此有守门测试;
③runtime tree 四版未变——服务运行时无需再审;④**只做阶段一本身就是最强对冲**:
阶段一完全可逆(genesis 前删除 review copy 重来即可),不消耗一次性名额,
b65fdc2 未复核的风险被"不越过不可逆点"完全兜住。

**仍悬着(按优先序)**:
1. b65fdc2 那批修复需要**一次非作者核对**再跨不可逆点(codex 事后复审、或人按
   票据 §4 实证清单抽验均可,不必是 panel);
2. runbook 零测试的机制原封未动——最低限度可执行化:一条自动断言"runbook 引用
   的每个文件存在于封印树"就能挡住轮2 那类 P0;
3. 把七轮攒下的各次"真实产物实证"固化为每次重建后的标准动作清单;
4. 摘出的账户加固四缺陷(主组 staff、⊆ 校验、属性不复验、root 闸 fail-open)
   实机当前无暴露,但票据死线是 §8 服务启动前必须交付;
5. genesis 仍不可排练——阶段 2B 每步仍是"首次执行即生产";
6. 残余风险实为 **4** 条:勿漏第 4 条 LIVE_PILOT / AUTONOMOUS_QUAL 未资格化、
   保持 BLOCKED(session 终局汇报只列了 3 条,这正是双权威漂移的又一实例)。

## 5. 本复盘的诚实性说明

综合初稿被三个对抗核验器抓出并已修正的主要错误:"7 个 P0"为选择性计数(全口径
约 10 个);"轮7 100% 回到基线"过强(P2 在代写脚本上);"累计 15 文件 +2497/−48"
与 git 不符(实测 936fdd7..b65fdc2 = 17 文件 +2513/−61);c3ef80b 为 5 处落笔、
确认 codex 老伤 2 条(非"一半");一处引文张冠李戴(session 语被标为报告明文);
残余风险漏计第 4 条;时间压力起点应为轮2 修复(非"我要快")。
