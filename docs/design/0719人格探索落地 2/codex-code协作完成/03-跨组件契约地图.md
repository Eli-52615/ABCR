## 2. 仍不一致 ⚠️（**真实产物在每一点上都通过**，故均非当前 P0/P1）

> **重要判断**：以下没有一条是「当前会炸」的。code 有意**不修**——复盘的核心结论是
> 「为加固而扩大受审面」是自引入 P1 的主要来源（第五轮即因此翻车）。
> 列在这里是为了 ①codex 验证时重点看 ②将来加固时有清单。按爆炸半径排序：

### 2.1 receipt / active.json 的 mode 宽严不齐
- **严侧**：`seal_broker:131`、`genesis:528+`、`qualify:169` 要求**恰好** `0440`（active.json 为 `0444`）
- **宽侧**：`install:543`、`abcr-launch:276`、`selector:152` 只要求 uid==0 且 `& 0o022 == 0`
- 后果：一个 `0444` 的 receipt 会被 broker 拒、被 launcher 接受。真实产物落在 `0440` 侧（broker 自己写的）。

### 2.2 receipt 字段集分歧（`genesis_pending` 能否通过）
- **校验字段集**：`install:549`、`qualify:159`、`genesis`、`mission_pipeline:34` → 多一个字段即拒
- **不校验**：`abcr-launch:276`、`selector:152`、`seal_broker._load_receipt:126`
- 后果：带 `genesis_pending` 的 receipt 会被 launcher/selector **接受**，被 installer/qualify 拒。

### 2.3 单文件字节读取上限四种取值 ← **最接近下一次爆炸**
| 位置 | 上限 |
|---|---|
| `abcr-launch:217`（`_scan_tree`） | 1 GiB |
| `selector:202`、`genesis:205` | 128 MiB |
| `selector:209`、`abcr-launch:352,355` | **8 MiB**（用的是默认值） |
| `install:211`、`worktree.py:33`、`release_policy:296` | 无上限 |

**真实最大单文件 43.3 MiB** —— 离 128 MiB 只有 3× 余量。**加一个 numpy/torch 级依赖就会踩线。**
另注：轮7 虽把 manifest 读取点统一到 128 MiB，但底层「防呆默认值」仍是老值
（`install:133`=4 MiB、`genesis:151`=4 MiB、`launch:92`=8 MiB、`selector:74`=8 MiB），
**任何新写的读取路径只要用默认值就会重新踩中轮7 那个坑**。

### 2.4 三个 `tree_hash` 的语义差异全靠注释维系
| hash | 含 manifest 自身？ | mode 是封印前还是后？ |
|---|---|---|
| `manifest.tree_hash` | 不含 | 封印**前**（0444/0555） |
| `receipt.tree_hash` | 含 | 封印前 |
| `receipt.sealed_tree_hash` | 含 | 封印**后**（0440/0550） |

两者相差**一条 22.82 MiB 的记录 + 20,417 个 mode 值**，却没有任何断言区分。

### 2.5 `qualify` 对异常类名的字符串耦合 ← **最隐蔽**
`qualify:484` 把 `exc.code == "FileNotFoundError"` 当作「对方已 ack」；该字符串来自
`seal_broker:852` 的 `type(exc).__name__` 兜底。**任何把 `SpoolError`/`FileNotFoundError`
改成 `ContractError` 的重构都会静默破坏 qualify 的判定分支，且无任何测试锚定。**

### 2.6 其余
- `seal_broker._verify_policy:173` 用**磁盘当前 mode** 推期望值 → 自证循环：若 `_apply_policy`
  把某 0555 文件错封成 0440，它会因「它现在没 x 位所以期望 0440」而放行；只有
  `install:1468` 与 `abcr-launch:261`（用 **manifest 声明 mode**）能抓到。
- `install` 用到但**未列入启动预检**的用户私有组（`abcr-verifier`/`abcr-activator`/
  `abcr-itempool`/`abcr-builder`/`abcr-candidate`）→ 缺失会在 `install_directories()`
  **中途**炸，此时已开始 mutate。
- dataset 策略同一事物两套编码：authority JSON 用字符串 `"0550"`，磁盘校验用 int `0o550`，
  两者之间无转换校验。

## 3. 无人持有假设的空白（潜在下一个 P0）

1. **staging / `export_plain_tree` 的目录 mode**：`worktree.py:88` 造 0700 根 + umask 子目录，
   而实测真实 staging 是 **0555** —— 说明有一步 chmod 发生在代码之外（runbook 或人工），
   **代码里没有任何一处声明 staging 目录 mode**。这是清单里唯一「零代码持有」的项。
2. **路径长度上限**：真实最长 151 字符，全系统零断言。
3. **`.gz` 被 `tarfile.open("r:*")` 以 0 成员成功打开**，于是两侧都在 `_scan_tar` 阶段
   `return True`，该 `.gz` 的解压内容**从未被扫描**。两侧一致故非分歧，但是**共享盲点**。
4. `ops/sandbox/abcr-candidate.sb:35` 对 releases 目录是 allow 还是 deny 上下文 —— **待核**
   （`abcr-release-read` 成员不含 `abcr-candidate`，`path-ownership-v1.json` 亦 `must_deny`）。
